# 本地部署 MiniMax H3：ComfyUI + INT8 量化

> 口径说明：本文只写实测过的配置和数据，不是从网上抄的通用教程。凡是没在你机器上跑过的，只写"未实测 / 未验证"，不写成定论。
> 远程操控通道（Tailscale + SSH + RDP + ComfyUI 局域网）见 `docs/setup-guide.md`；通用故障速查见 `docs/troubleshooting.md`。本文只讲 H3 本身。

## 1. H3 是什么、本地能跑哪个版本

- MiniMax H3 是 MiniMax 2026 年 8 月开源的视频生成模型，约 33B，全模态、原生带音频。
- **本地开源的只有 H3-Base**，本地输出上限约 768p。
- **Context-IR、Regenerate-2K 没有开源，只能走官方 API**。2K 成片的官方路线是 Regenerate-2K API，或者本地出 768p 后再后期放大。
- 社区许可排除美国 / 欧盟 / 英国 / 韩国用户，中国用户可用。
- ComfyUI 已官方支持 H3，不用自己搭推理框架。
- 注意：预装工作流页里 Seedance 2.5 Reference to Video 卡片标注"需要积分"，那是云端付费工作流，**Seedance 不能本地部署**，不要把它算进本地清单。

## 2. 硬件档位（以 16G 显存 + 32G 内存的机器为锚点）

| 模型 / 版本 | 结论 |
|---|---|
| MiniMax H3-Base（INT8 量化，ComfyUI） | **可以**。16G 显存推荐方案，权重约 40G，运行时显存约 14G。1280×736、5 秒已跑通 |
| MiniMax H3-Base（更高精度 / 未量化版） | **未实测，不写定论**。不要默认 16G 也能同等跑 |
| MiniMax M 系列（M1 / M2 / M3，428B 级 MoE） | **即使内存升到 64G 也扛不动**。本地可跑的 MiniMax 模型只有 H3 |
| H3 的 Context-IR、Regenerate-2K | **本地没有，只能走 API** |

其他模型家族（同一台机器，2026-10-19 评估口径）：视频生成 Wan 2.1、CogVideoX-5B、LTX-Video 可以；HunyuanVideo 13B 显存吃力，不推荐。图像 SDXL、Flux 量化版、Qwen-Image 量化版可以。Ollama 大语言模型 14B 及以下全显存跑，32B 需部分 offload。

一句话：**这台机器的本地视频主力就是 H3-Base INT8；想上更大模型，瓶颈在显存，不在 CPU。**

## 3. 部署步骤（已跑通）

### 3.1 前置条件

1. Windows 专业版、管理员账号可用、接有线或稳定 Wi-Fi、电源设从不睡眠。
2. 磁盘留足空间：T2V 一次约 53GB，R2V 再加约 19GB，turbo LoRA 约 1.82GB，成片和中间文件另算。
3. 驱动要够新：ffmpeg 9.0.2 要求 NVENC API 13.1、驱动 610.00+，旧驱动会直接报错。

### 3.2 安装 ComfyUI Desktop

1. 装 ComfyUI Desktop，安装器里没有"本地部署 / 镜像加速"选项时不用找，直接下一步。
2. 运行方式页选"本地"，再选 NVIDIA GPU，版本 v0.42.1。
3. 预装工作流页点第一张 MiniMax H3 Text to Video 卡片（标注"推荐"），点安装，约 53GB 模型随安装下载。
4. 验证：T2V 工作流已跑通，正常生成出第一条 5 秒视频。

找模型目录的实测技巧：ComfyUI Desktop v0.42.1 左上角 ≡ 应用菜单里**没有** Help → Open Folder 入口，不要在菜单里耗。直接在文件资源管理器里搜一个已有的模型文件名，右键"打开文件所在的位置"即到 `diffusion_models`。模板库在左侧边栏的四宫格图标里，Video 分类下有官方 MiniMax H3 T2V / 图生视频 / 参考生视频三个模板。

### 3.3 三条工作流的关系

| 工作流 | 模型关系 | 是否要另下载 |
|---|---|---|
| Text to Video（T2V） | 主模型 FL2VA | 随预装工作流一次下载，约 53GB |
| Image to Video（I2V） | 与 T2V 共用同一套 FL2VA 模型 | 不用重下。同一节点两种用法：first_frame 留空就是文生视频，接一张首帧图就是图生视频 |
| Reference to Video（R2V） | 独立的 ref2va 模型 | 要另下载，见下 |

R2V 的两个关键文件：

- 主模型：`minimax_h3_ref2va_pruned_int8_convrot.safetensors`，约 19GB，来源 ModelScope 的 Comfy-Org/MiniMax-H3，放进 `diffusion_models` 文件夹。
- 可选加速：turbo LoRA，约 1.82GB。默认打法是 **turbo 4 步跑试词、提示词定稿后关 turbo 用 20 步标准模式出正式版**。两者采样轨迹不同，同种子构图也可能有小偏差，定稿漂移就换种子重跑 20 步。

## 4. 分辨率与步数：两个定论

| 设置 | 定论 | 原因 |
|---|---|---|
| Resolution Selector（分辨率选择器） | **定 0.9，即 1280×736** | 该版本步进器只有 0.9 / 1.0 两档，没有 0.98；1.0 = 1376×768，会超 H3-Base 像素面积上限，官方文档明确勿用 |
| 步数 steps | **原生节点固定 20 步，界面没有 steps 可调** | 不要再去找 steps 滑杆 |

工作习惯：832×480 低分辨率抽卡试错，选定后再跑高分辨率成片。32G 内存是最低门槛，实测内存占用约 44G。

## 5. R2V 接线与两段式换人

### 5.1 接线铁律

**MiniMaxH3ReferenceToVideo 节点的 ref_video 输入类型是 IMAGE，不是 VIDEO。**

正确接法：

```
LoadVideo 的 VIDEO 输出
  → GetVideoComponents（获取视频元素）的 video 输入
    → 它的 images（帧图）输出 → ref_video_0
    → 它的 audio 输出 → ref_video_audio_0（可选，给参考视频配原声）
```

直接把 VIDEO 输出拖到 ref_video_0 必失败，套接字圆点颜色也能佐证：IMAGE 是蓝色，和 ref_image 同色。

其他 R2V 要点：

- 参考素材上限：最多 9 张参考图 + 3 段参考视频 + 3 段参考音频。
- 提示词用中文写，但 `<Picture 1>` / `<Video 1>` / `<Audio 1>` 这类标签保持英文原样，且标签序号必须和连线顺序一致。
- 模板本身不带"加载视频"和"获取视频元素"节点，这两个是手动加的。
- Load Video 选文件要在节点本体上选 input 目录里的纯文件名。在右侧 Nodes 面板文本框里改值不写回节点本体，白改。文件不在 input 时，先把文件拷进共享目录的 input 文件夹，再在节点本体点 file 字段选纯文件名（不带任何后缀）。
- 成片取法：SaveVideo 的 history outputs 挂在 images 键下，不是 videos；产物在 output 文件夹。

### 5.2 两段式：R2V 换人必须走的路线（实测结论）

**模型铁律：成片的人只看视频里的人，照片抢不过视频。**

只要参考视频里有清晰正脸，成片人物必是视频里的人。实测连试四次全部失败，杠杆都试过了：换提示词分工（否定式与正向式各一版）、视频降帧至 4fps / 40 帧、再加一张同人物全身照占 ref_image_2，全都不行。

唯一可行解是两段式：

- **第一段：只换人，背景不动。** 用参考视频 + 目标人物肖像，产出 1280×736、5 秒左右带原声的换人版。核验标准：主角确已换成目标人物，舞蹈和背景不变。
- **第二段：再以第一段成片为 Video 参考，做三合一合成。** 这时所有参考素材的身份先统一了，Ref2VA 就不会选错。核验三要素：人物未漂移、背景换成目标背景（例如赛博朋克街道）、原版舞蹈动作保留。

## 6. 生成耗时实测（1280×736、5 秒，同一台机器）

| 任务 | 模式 | 实测耗时 |
|---|---|---|
| R2V 纯图片参考 | 20 步标准 | 约 12.6 分钟 |
| R2V 纯图片参考 | turbo 4 步 | 约 2.7 分钟，约快 4.7 倍，静帧质量无明显缩水 |
| R2V 带视频参考（第二段） | turbo | 约 11–12 分钟 |
| 带视频参考为什么慢 | — | 每步采样都要重读视频参考帧，16G 显存吃紧；在 Windows 本机点运行也不会更快，Mac 只是浏览器控制面，不调用 Mac 硬件 |

估时基准：纯图参考按 turbo 约 3 分钟 / 20 步约 13 分钟估；带视频参考按 turbo 约 11–12 分钟估。

## 7. Mac / Windows 渲染分工（ffmpeg NVENC）

总原则：Mac 当大脑和审片台，Windows 当 GPU 渲染和生成机。Mac 是脚本、EDL、成片的唯一真源；Windows 只出渲染结果和生成素材，不改 Mac 的源文件和 EDL。大视频文件别来回传，任务放素材所在的那边做，只传回成片和日志。

- **小样 Mac 本地出、批量长段 Windows 并行、最终 Mac 定稿。**
- 日常：剪完一段，先在 Mac 用 VideoToolbox 出小样立即审，不走隧道、不等传输。
- Windows 并行与批量（满足任一才用）：要同时出多版本、单段较长、或 Mac 要继续剪不能被渲染占住时，把源片一次性发 Windows，用 NVENC p7、8M 渲，只回传成片 MP4 与渲染日志，Mac 继续剪不用等。
- 传输规则：源片只发一次、文件名锁定；不来回传中间文件；回传只传成片，不传工程与中间帧；传输走后台 scp，不阻塞剪辑。
- 最终成片（锁在 Mac）：VideoToolbox，720p 用 8M、1080p 用 10M，yuv420p、30fps，音频直接复制或 AAC 192k，参数冻结后不再换编码器与码率。
- 命名：`<项目>-<日期>-draft-<编码器>-<码率>-v<n>.mp4`；每渲一次记一笔：源片、参数、耗时、大小、审片结论，下次直接复用，不重新试参数。

实测数据（30 秒合成小样与真实口播素材，同定码率对照）：Windows NVENC 比 Mac VideoToolbox 快约 1.4–1.5 倍；同定 8M 时 Mac 实际码率约高 14%，同码率下肉眼基本分辨不出差别，成片经平台再压后差别基本会被抹平。

**概念纠正：渲染不经过大模型，agent 只是写命令的人，执行的是 ffmpeg 的编码器（NVENC / VideoToolbox）。画质差距不是本地部署模型导致的。**

## 8. H3 专属坑速查

| 症状 | 定位与处理 |
|---|---|
| 分辨率 1.0 报错 / 生成失败 | 1.0 超 H3-Base 像素面积上限，定回 0.9（1280×736） |
| 找不到 steps 滑杆 | 原生节点固定 20 步，界面没有 steps 可调，不用找 |
| ref_video 连不上 / 报类型错 | ref_video 是 IMAGE 不是 VIDEO，参考视频先经 GetVideoComponents 拆成帧图再连 ref_video_0 |
| R2V 成片人物不是目标人物 | 照片抢不过视频，走两段式：先只换人、背景不动，再以换人版为参考合成 |
| 前端报 Missing Models | 先确认四个模型联接还在，再点 Issues 的 Refresh，不必整页刷新 |
| Load Video 选不到文件 / 值改了没用 | 文件先拷进共享 input 文件夹，在节点本体选纯文件名；右侧面板改值不写回本体 |
| 成片找不到 | SaveVideo 的 history outputs 挂在 images 键下，不是 videos；去 output 文件夹找 |
| ffmpeg 报 NVENC API 版本不支持 | 驱动太旧，ffmpeg 9.0.2 要求 NVENC API 13.1、驱动 610.00+，更新驱动再渲 |
